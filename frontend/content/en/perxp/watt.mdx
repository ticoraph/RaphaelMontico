# Watt: household energy tracking and forecasting

## Context

[Watt](https://watt.tnera.fr) is an application I developed to bring together my electricity consumption, solar production, vehicle charging, home sensors, weather, and water readings. It replaces scattered exports with a shared daily time series that can be viewed and used for forecasting.

The product combines a dashboard, source-specific views, feature engineering, time-series model comparisons, an MLflow registry, and an analysis report generated locally by an LLM.

## Problem

Each provider imposes its own access method and format. Enedis provides exports, EcoFlow and Tesla require reusing app captures, Aqara stores part of its history in a local SQLite cache, water readings are only available a few times a year, and weather comes from another source.

These data have different granularities, units, and time periods. Aggregating them without duplication or overwriting, then fairly comparing zero-shot, supervised, and seasonal models, required a reproducible pipeline and shared backtests.

## Solution

I developed an importer for each source, followed by a pipeline that produces a deduplicated daily CSV for Enedis, EcoFlow, Tesla, Aqara, water, and climate. The files are joined by date, cleaned, and enriched before being imported idempotently into SQLite. The schema adapts to new columns and fills only values that are still missing.

Feature engineering calculates, among other things, solar yield per hour of sunshine, residuals relative to a trend, the off-peak share net of Tesla and heat pump consumption, and temperature range. The dataset feeds XGBoost, TimesFM, Chronos2, Prophet, and a seasonal average. Each script produces the same backtest format; MLflow records parameters, metrics, and models, then a manual promotion selects the version used for forecasting with p10/p50/p90 bands. A quantized Qwen3-4B analyzes errors and anomalies offline in French.

## Architecture

```text
Enedis │ EcoFlow │ Tesla │ Aqara │ Water │ Weather
                    │
        imports and daily time series
                    │
        joins + transformations + features
                    │
                 SQLite
          ┌─────────┴─────────┐
          ▼                   ▼
       FastAPI          ML training
          │          XGBoost / TimesFM /
          │          Chronos2 / Prophet
          │                   │
          │                 MLflow
          │                   │
          └──── React ── forecasts + Qwen report
```

A Makefile and Prefect flow orchestrate preparation, training, promotion, and analysis. Steps that require a connection or a mobile capture remain explicit in the monthly runbook.

## Deployment

The FastAPI API and MLflow server are deployed in two Google Cloud Run services. The React/Vite frontend is published on Firebase Hosting, which rewrites `/api/**` and `/mlflow/**` to the corresponding services to preserve a single origin. Google authentication uses Firebase Auth and an allowlist verified on the API side.

GitHub Actions uses Workload Identity Federation, with no static JSON key, to build the images, publish them to Artifact Registry, and deploy the services. The SQLite database, forecasts, and validated MLflow registry are bundled as read-only artifacts in the published version. CI runs Ruff, Pytest, and the frontend build.

## Impact

Watt makes consumption, peak power, costs, solar production, charging, temperatures, and precipitation since 2022 viewable in one place. Backtests for five approaches can be compared by MAE, RMSE, bias, and MAPE; the selected forecast displays its uncertainty rather than a single figure.

The MLflow server is accessible in the deployed application, while the Qwen report explains differences between models without sending household data to a remote LLM service. Model selection remains a human decision based on backtests, not an automatic promotion triggered by CI.

## Learnings

I learned that a personal time-series project is first and foremost an acquisition and data quality problem. Provider limitations—short-lived tokens, partial caches, annual readings—must be reflected in the pipeline and in the model assumptions.

Comparing very different models also taught me to enforce a shared protocol and retain a simple baseline. Finally, separating offline computation from the read API makes the cloud service more predictable: the application serves validated artifacts without triggering training or a heavy LLM on every visit.
